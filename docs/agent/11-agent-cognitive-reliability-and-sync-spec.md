# Mira Agent 认知可靠性、注意力工程与全链路状态同步设计规范 (Cognitive Reliability, Attention Engineering & State Sync Spec)

本文档沉淀自“剧本角色提取与出处锚定”多轮深度调优（从早期的 11 处散落规则冲突、被动动作漏检、静默心算错位、“可能呈现”引发 53 处全选、防覆盖警告导致漏建二级版本，最终演进至 **10 轮闭环、32 处真实出场零误选、多版本精准拆分离落盘**），作为后续修改或新增代码、Prompt 撰写、工具设计及架构讨论的**强制性工程规范与基础背景共识**。

> **核心心法**：模型“不听话”几乎从来不是因为“态度叛逆”，而是因为**判准边界模糊、多处规则口径冲突、思考跳步（概括性脑补）或缺少合法的信息分流出口**。所谓“让模型听话”，本质上是通过**「纯正向的必要条件判准 + 职责归位的单一事实源 + 分批精读下的逐句原文核查 + 显式分流与代码托底的工具契约 + 按阶段物理隔离的上下文」**，把模型达成目标的“阻力最小路径”设计成我们期望的正确路径。

## 法则一：Prompt 撰写法则——纯正向必要条件、通用抽象与单一事实源 (SSOT)

1. **纯正向必要条件判准（只写“要怎么做”，不列“严禁清单”，收紧为必要条件）**
   - **踩坑教训**：
     - **负面禁令清单失效**：堆砌“严禁将他人台词、纯画外音、纯心理活动、转场标记纳入出处”，不仅引发“白熊效应”增加内耗，而且负面清单永远列不全（防了台词却漏防了道具特写 `▲镜头特写：救我——`）。
     - **过窄的正向条件漏检**：写“若该资产在当前画面中有明确可见的**自身动作**”，会导致角色作为动作承受方（如 `▲小玛莉一把将小娜塔莉亚推向了养父`）时被误杀。
     - **过宽的正向条件泛滥**：写“如果资产**可能**在画面中呈现出来”，模型会推导出“虽然这 18 段是管家训话喂狼，但角色还在院子里没走（在场），画面可能拍到她 ✅”，导致出处暴涨至 53 处。
   - **工程准则**：用一句高内聚的**正向必要条件**替代所有负面清单：
     > **“根据段落内容，如果该资产必须出现在画面中才能呈现该段落，则判定该段落为出处”**
     凡是他人单人台词、道具空镜特写、群演反应或转场标记，不需要该资产入画也能拍出该段落，自然被模型干净排除；而自身动作、神态、特写、当场台词或被动受力的交互镜头，必须有该资产入画才能呈现，自然 100% 召回。

2. **规则必须抽象通用，严禁堆砌具体剧本特例 (Zero Hardcoded Examples)**
   - **踩坑教训**：在规则中写入具体剧本例子（如“像小娜塔莉亚这种童年闪回要建版本”或“像‘救我’这种特写不要选”），会让模型把注意力窄化到字面匹配的特例上，换一部剧或换一种场景即失效。
   - **工程准则**：所有规则必须抽象为领域内通用的结构化维度（如*“角色处于不同年龄阶段或不同服装造型、场景处于不同日夜状态、道具处于不同形态状态”*），依靠通用逻辑泛化。

3. **单一事实源与职责归位（Single Source of Truth & Tool-Scoped Rules）**
   - **踩坑教训**：早期出处规则同时散落在 11 个位置（全局提示词、执行提示词、状态提示词、工具简表、工具详情、工具返回值 `instruction`、前端校验提示词等），各处措辞微有差异，改一处漏十处。
   - **工程准则**：
     - **全局只保留 1 处权威定义**，彻底清理重复与冲突描述；
     - **通用指南与工具规则严格分家**：`systemPromptExecution.txt` 只放跨任务通用的执行流转原则；特定工具的参数判定标准（如 `provenances` 出处规则、`versions` 版本划分规则）必须就近内聚在 `src/agent/toolRegistry.ts` 对应工具的描述中。

## 法则二：推理与注意力工程——分批精读 + “逐句输出原文进行判断”

1. **为什么不能让模型“静默心算”直接报序号？**
   - **踩坑教训**：去掉思考区的逐段输出要求、让模型直接输出 `paragraphIndices: [1, 2, 3, 6, 7]` 时，模型会凭模糊印象成片抓取，导致误抓道具特写段、漏掉散落的交互段，甚至把第 25/26 段的序号错记为 24/29。

2. **为什么只要求“按段落序号显式逐条输出判定结果”还不够？**
   - **踩坑教训**：只要求输出段落序号与结果时，模型会用 3~4 个字自己概括段落（如 `段2：养父台词 → 通过`、`段6：对她叮嘱 → 通过`）。一旦模型用“对她叮嘱”代替了原句，它就会脑补“既然是对她叮嘱，那她肯定在画面里”，从而把纯他人台词多选进来。

3. **终极解法：“分批精读 + 按段落序号逐句输出原文进行判断”**
   - **宏观分批控制单轮扫描长度**：通过检索数据量预警触发 0 级动态重规划，将跨多场次任务拆解为每次精读 1~2 个场次（约 10~40 段）的合理批次，避免单轮硬吞全集上百段导致输出 Token 耗尽。
   - **微观强制带着原文判断**：在工具描述中明确要求**“核实出处时须在思考中按段落序号逐句输出原文进行判断并显式逐条输出每段判定结果”**。自回归生成机制会迫使模型在输出 `出 / 不出` 之前，先把该段原文的**实际主语和画面内容**（如 `段4“镜头特写：救我”为照片特写，娜塔莉亚不必在画面→不出；段23“布拉姆打量”主体→不出`）加载到当前注意力窗口中，彻底消灭行号错位、漏段与“凭脑补在场多选”。

## 法则三：工具契约设计——显式 If-Else 分流导航、指针化入参与底层托底

1. **用显式 If-Else 分流导航替代模糊的“或”字与过度防御警告**
   - **踩坑教训**：在分步建卡（第 1 场只有单一成年造型，未初始化 `versions`）后，读到后续场次的童年造型时，模型之所以未建二级版本，是因为：
     1. `asset.update` 写了“修改二级版本列表（`versions`）**或**补充出处段落（`provenances`）”，被模型当成二选一；
     2. 工具描述警告“若仅补充出处请勿传残缺的单场 `description` 覆盖已有简介”，吓得模型开启过度防御（“为避免覆盖，本轮只传顶层 `provenances`，不动已有 `description` 与版本”），把童年出处直接塞进了成年主卡。
   - **工程准则**：在工具描述中提供清晰的 If-Else 分流路径，并展开完整参数签名：
     - **背景信息 vs 画面出处分流**：相关背景信息归入 `description`，必须入画的段落归入 `provenances`；
     - **同造型追加 vs 新造型建版本分流**：
       * 当所读场次中资产仍为**已有造型或状态**时 $\rightarrow$ 直接在顶层传 `provenances` 增量追加出处（仅追加出处时无需传顶层 `description`）；
       * 当所读场次中资产呈现出**与已有造型不同的新视觉造型或状态**（角色处于不同年龄阶段或不同服装造型、场景处于不同日夜状态、道具处于不同形态状态）时 $\rightarrow$ 必须通过 `versions` 数组传入该新版本对象（`versions?: Array<{ name, description, appearance, aliases, provenances }>`），将该造型对应的场次出处直接绑定在该新版本下。

2. **底层代码确定性托底（主卡自动升格 + 1-based 指针映射）**
   - **主卡自动升格托底**：当资产最初以单一版本建卡（`versions` 为空），后续通过 `asset.update(mode: "append", versions: [...])` 追加首个新造型版本时，`projectTools.ts` 自动将原主卡造型升格为 `versions[0]` 并与新版本并列保留；后续对顶层追加的同造型出处也会自动同步至 `versions[0]`。
   - **1-based 连续序号与指针化入参**：`script.read` 返回 `index: 1..N` 连续段落序号并原生支持场次数组批量读取（如 `scene: ["1-2", "1-3"]`）；写入工具只收 `sceneTitle` 与 `paragraphIndices: [1, 2, 3]`，由底层代码确定性映射真实行号与 `evidenceText` 原文。

## 法则四：分层认知与按需暴露——物理级注意力隔离 (Dual-Level Staged Cognition)

1. **0 级全局规划与 1 级局部执行物理拆离**
   - **0 级全局规划与验收 (`systemPrompt.txt`)**：仅暴露 `sys.selectContext`、`sys.endTask`、`user.ask`，专注拆解分步计划、按需挑选工具并在最后验收结案。
   - **1 级局部专注执行 (`systemPromptExecution.txt`)**：仅注入当前装载的具体业务工具 Schema，围绕“当前计划”中的 `[ ]` 步骤连续调用工具推进。
2. **用“工具可见性”代替口头警告**
   - 探查期（数据未知时）仅装载只读工具组 `[script.directory, script.search, asset.list]`；获知场次分布后，一次性成套装载读写工具组 `[script.read, asset.create, asset.update]` 执行分步精读与随读随写。

## 法则五：指针化与全链路对称同步——杜绝认知分裂与防御性回查

1. **区分“不可变意图快照”与“可变环境真值”**
   - 用户初始指令（`initialGoal`）与划词片段（`scriptSelection`）冻结为意图快照；面板统计计数、聚焦资产属性、卡片状态则以 `targetId` 指针为核心，每次消费前通过纯函数 `refreshTaskCardContext(cardContext, project, allCards)` 实时派生。
2. **“写后即刷 + 读前必刷”与契约级定心丸**
   - 任何 Mutation 工具落盘后立即原地刷新 `task.cardContext`，并在工具描述中明确声明*“落盘返回即为真值，无需调用 asset.list 回查”*，切断防御性冗余轮次。
   - 每次修改默认提示词后，同步在 `server.ts`（`isObsoleteMainPrompt`）与 `src/utils/promptPersistence.ts`（`isObsoletePromptText`）中标记旧特征词过期，确保前后端缓存自动刷新。
